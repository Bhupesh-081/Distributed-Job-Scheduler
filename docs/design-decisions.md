# Design Decisions

## Backend: Go, not Go-only
The reliability/concurrency requirement (atomic claiming, concurrent execution, graceful shutdown, worker pools) is the core engineering challenge here and is worth 15+20=35 of the 100 grading marks combined with architecture. Go's goroutines/channels and mature Postgres/Kafka drivers map directly onto that without a framework doing it for us - which keeps the concurrency logic visibly our own engineering rather than hidden inside a library (e.g. Celery, BullMQ), which is what the assignment is grading. Existing auth/org/project code (`cmd/api`) and the core job pipeline stay Go by default, but a new component can use a different language if it's a meaningfully better fit for that component (e.g. a stronger library for one job-executor type) - robustness of the overall system outranks stack uniformity. Any such choice gets called out here with the tradeoff (extra runtime to build/deploy), not introduced silently.

## PostgreSQL as source of truth
Chosen over MySQL for `SELECT/UPDATE ... WHERE ... RETURNING`, native `jsonb` (job payloads are arbitrary per job `type`), and strong constraint/index support for the required entity list. It is the single authority on job state - every other component (Kafka, Redis) is a cache or transport in front of it, never a second source of truth. This avoids split-brain between "what Kafka thinks is queued" and "what actually happened," which is the most common reliability bug in job systems.

## CAP tradeoff: availability over consistency
The assignment's NFRs call this out explicitly (10K jobs/sec, at-least-once execution, 2s scheduling latency - see [architecture.md](./architecture.md#non-functional-requirements)). We favor a component staying up and making progress (Kafka partitions, Watcher polling, workers claiming) over every reader seeing the latest job status instantly. Postgres remains the single strongly-consistent source of truth for job state; everything in front of it (Kafka, Redis) is allowed to be eventually consistent/stale by design, which is why the atomic-claim step against Postgres - not message delivery - is what actually prevents duplicate execution.

## Kafka as transport, not authority
Kafka gives push-style delivery at the required throughput (10K jobs/sec) and partitioned topics (`run`/`retry`/`dead`) map onto the job lifecycle's happy path, retry path, and dead-letter path. Kafka only guarantees *at-least-once* delivery, so it cannot be trusted alone to prevent duplicate execution - every worker still performs an atomic conditional `UPDATE` against Postgres before treating a message as claimed (see [architecture.md](./architecture.md#job-lifecycle)). This is deliberately more infrastructure than a pure DB-backed queue (Postgres `SKIP LOCKED` alone would have worked), chosen because the assignment explicitly rewards a "production-inspired" design and lists event-driven execution as a bonus feature - but the atomic-claim logic is kept regardless, so if Kafka were ever removed the correctness guarantee wouldn't change, only the latency would.

**Known gotcha (found wiring `docker-compose.yml`, fixed):** a consumer that joins its Kafka group before its topic exists gets assigned zero partitions and - with `segmentio/kafka-go`'s default `Reader` config - stays stuck there forever, even after the topic is created by the first real publish. This bit consumer-service specifically on a fresh `docker compose up`: watcher-service and consumer-service both start immediately, but the `run`/`retry` topics don't exist until the first job is actually dispatched, which can happen after consumer-service has already joined its group with an empty topic. `internal/kafka.NewConsumer` now sets `WatchPartitionChanges: true` on the `kafka-go` `ReaderConfig`, which makes it periodically recheck and rejoin when partitions appear. Confirmed live: without the flag a job published after a fresh stack start sat `queued` indefinitely (only recovered ~30s later via watcher-service's stuck-job requeue, and then only because a *second* consumer instance would've had the same problem); with the flag the same scenario executes in under 5s.

## Redis: two real jobs, everything else moved to Postgres
The original plan for this section (worker heartbeats, in-flight concurrency counters, and watcher-service's polling watermark all living in Redis) didn't survive contact with implementation. Consumer-service worker heartbeats/liveness ended up as real `workers`/`worker_heartbeats` Postgres tables instead (needed as graded DB entities regardless, and a poll-driven watcher-service that already hits Postgres every second has no latency reason to also hit Redis for the same liveness check). The concurrency-limit counter is a `count(*) FROM jobs WHERE queue_id=... AND status='running'` inside `ClaimJob`'s transaction, guarded by a Postgres advisory lock - not a Redis counter, since it has to be transactionally consistent with the claim itself. The polling watermark is just `jobs.dispatched_at IS NULL` - a column, not a cursor. What Redis actually does, today: (1) `internal/cancel`'s `cancel:{jobID}` TTL key, set by job-service on `POST /jobs/{id}/cancel` and polled by consumer-service during execution; (2) `internal/heartbeat`'s `watcher:last_poll` key - watcher-service is a *single instance* with no Postgres-backed liveness table of its own (unlike consumer-service's worker fleet, which has one), so Redis is where its self-reported "still ticking" signal lives, read by `cmd/api`'s `GET /system/health`. Losing Redis loses the ability to cancel a job that's already running (it just finishes instead of aborting early) and the ability to tell whether watcher-service is alive from the API - nothing that affects job correctness. See [architecture.md](./architecture.md#services) for the current, accurate picture.

## watcher-service as its own service
Polling "what's due" (now including expanding due `scheduled_jobs`/cron definitions - see [architecture.md](./architecture.md#recurring-cron-jobs)) is cheap but must not compete with API request handling or run multiple times concurrently, which would double-publish jobs. Splitting it into its own binary keeps that logic independent of how many `cmd/api`/`cmd/job-service`/`cmd/consumer-service` replicas exist. **Currently deployed as a single instance with no leader election** (`ponytail:` comment in `cmd/watcher-service/main.go`) - a second replica really would double-publish today. A Redis or Postgres advisory lock for leader election is the documented upgrade path once running more than one becomes necessary; not built because nothing in this deployment needs more than one yet.

## Frontend: React + Vite
A plain SPA talking to the REST API is the right amount of frontend for a dashboard whose job is to display and act on backend state (queues, jobs, workers, logs) - no SSR/SEO need exists here, so Next.js's extra structure buys nothing. Live updates start as polling (simplest thing that works); WebSockets are listed as a bonus and can be layered on the same API without a rewrite if time allows.

## What's deliberately deferred
Bonus items (not core requirements):
- Workflow dependencies (job DAGs), queue sharding, and AI failure summaries - not designed in detail here; the schema (`jobs.type`, `jsonb payload`) doesn't preclude adding a `job_dependencies` table later.
- RBAC beyond `org_members.role` (owner/member) - left coarse until core scheduling is solid.
- Web dashboard, DLQ viewer, metrics, distributed tracing - per the MVP build workflow's own skip list.
- Cron parsing - **done**, moved out of this deferred list: see [architecture.md](./architecture.md#recurring-cron-jobs) (`scheduled_jobs` table, migration `0010`, `internal/cronexpr`).

**MVP bootstrap ledger - graded core requirements, deferred to get one job running end-to-end first, not dropped. All 6 items below are now DONE**, each additive on top of the MVP schema (`jobs`/`job_runs`) as planned, no rewrite. Migrations `0005`–`0009` in `internal/db/migrations/`.
- **Project/queue scoping - DONE.** `queues` table (`project_id` FK, `priority`, `concurrency_limit`, `paused`) added in migration `0005_queues.sql`; `jobs.queue_id` FK (nullable at the DB level - pre-migration rows have none, but job-service's HTTP layer requires it on every new job). `ClaimJob` enforces `concurrency_limit`/`paused` per queue via a `pg_advisory_xact_lock` on the queue ID (serializes claims per queue without blocking other queues); a job blocked this way stays `status='queued'` with `dispatched_at` still set, so it's picked up again by watcher-service's existing stuck-job recovery once a slot frees - no separate retry path needed. `DispatchDueJobs` orders by queue `priority` (desc) then `scheduled_time`, and skips paused queues. Queue CRUD + pause/resume + stats live on `cmd/api` (authenticated, org-membership-checked) under `/projects/{projectId}/queues` and `/queues/{queueId}`; job-service (`POST /jobs`) requires `queue_id` on every job (auth added - see "Auth on job-service routes" below).
- **`retry_policies` table - DONE.** Migration `0006_retry_policies.sql`: `retry_policies` (project-scoped, `strategy` fixed/linear/exponential, `base_delay_seconds`, optional `max_delay_seconds` cap), `queues.default_retry_policy_id`, `jobs.retry_policy_id` (overrides the queue default). CRUD lives on `cmd/api` under `/projects/{projectId}/retry-policies` and `/retry-policies/{id}`. `store.RetryPolicy.Delay(attempt)` is the pure strategy calculation (unit-tested); `store.EffectiveRetryPolicy` resolves job override → queue default → `ok=false` (consumer-service falls back to its old hardcoded 5s). Live-verified: exponential 2s/4s/8s backoff observed via `job_runs` timestamps before dead-lettering.
- **`workers` / `worker_heartbeats` tables - DONE.** Migration `0007_workers.sql`: `workers` (current state: hostname, pid, concurrency, status active/stopped, started/stopped/last_heartbeat timestamps) + `worker_heartbeats` (append-only history: heartbeat_at, in_flight_count). `job_runs.worker_id` FK now records which consumer-service instance ran each attempt. Each consumer-service process self-registers a random UUID at startup, heartbeats every 10s (liveness + in-flight job count via an atomic counter), and marks itself `stopped` on graceful shutdown; watcher-service's existing poll tick reaps workers whose heartbeat is >30s stale (crash case), reusing the stuck-job-recovery pattern rather than a separate reaper process. `GET /workers` / `GET /workers/{id}` on `cmd/api` are authenticated but not project-scoped - the worker pool is shared infrastructure, not owned by one org. Live-verified: registration, heartbeat cadence, `job_runs.worker_id` attribution, stale-worker reaping, and SIGTERM → `status='stopped'` all confirmed against the real stack.
- **`job_logs` table - DONE.** Migration `0008_job_logs.sql`: `job_logs` (job_id, nullable job_run_id, level info/warn/error, message, created_at - message capped at 4000 chars). `job_runs.err_msg` stays as the one-line failure summary; `job_logs` is the browsable stream alongside it. consumer-service writes an entry at claim, at captured stdout/stderr output, and at each terminal outcome (success/cancelled/failed/dead-lettered/requeued). `GET /jobs/{id}/logs` on job-service returns them oldest-first (chronological, like a log tail - the one list endpoint in this codebase that isn't newest-first, deliberately). Live-verified: a successful job's 3-entry stream, and a failing job's full lifecycle across two attempts (claim → fail → requeue → claim → fail → dead-letter) with `job_run_id` correctly distinguishing attempts.
- **`dead_letter_queue` table - DONE.** Migration `0009_dead_letter_queue.sql`: `dead_letter_queue` (job_id, queue_id snapshot, final_error, retries_count, moved_at). Append-only like `job_runs`/`job_logs`, not a mutable single record - a replayed job that dies again gets a second row, which is itself useful history. consumer-service writes an entry in the same branch that sets `jobs.status='dead'`. `GET /queues/{queueId}/dlq`, `GET/POST replay/DELETE /dlq/{id}` on `cmd/api`, authenticated via the owning queue's org (an entry with no `queue_id` - an unscoped legacy job - has no owning org, so it 404s rather than being exposed to any authenticated user). Replay resets the job to `queued`/`retries_count=0`/`dispatched_at=NULL` and deletes the DLQ row; watcher-service picks it up on its next tick like any other due job. Live-verified: dead-letter → DLQ entry appears with the real error → replay → job actually re-executes (`job_runs` count went 1→2) → re-fails → fresh DLQ entry (new ID, confirming a real second pass, not a stale row) → delete removes the entry without touching the job's `dead` status → cross-org access correctly 403s.
- **Auth on job-service routes - DONE.** All `/jobs*` routes now require `Authorization: Bearer`, sharing `cmd/api`'s JWT secret (`authsvc.TokenIssuer`, refactored so both `Server.requireAuth` and `JobServer.requireAuth` delegate to one `requireAuthWith` - job-service only ever validates tokens, never issues them, so it needs no `AccessTokenTTL`). Access is scoped by the job's `queue_id` → the caller's org membership, reusing the same `requireQueueAccess` helper `cmd/api`'s queue endpoints already used (also extracted to a shared function rather than duplicated). `POST /jobs`/`/jobs/batch` check the target queue(s) before creating anything (a batch spanning an unauthorized queue creates nothing, not a partial batch); `GET/POST` on an existing job load it first and check its queue, with the same "no queue_id → 404, not 403" rule as DLQ entries for legacy pre-auth jobs. `GET /jobs` now requires `queue_id` (no more "list every job" - meaningless once scoped by org anyway). Live-verified against the real stack: no token → 401, wrong org → 403 (or 404 by ID), owning org → 200/201, a batch mixing an owned and unowned queue → 403 with zero jobs created, and the full create → dispatch → execute pipeline still passes end-to-end with a real bearer token.
